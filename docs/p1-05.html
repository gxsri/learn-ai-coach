路线 A · 多 agent 协作

05 · 实战复盘：这套文档是怎么被多 agent 生产出来的

这一篇不是理论。它记录的是就在你眼前真实发生过的一次多 agent 运行—— 你在这次会话里看到的那次 workflow 调用。

学会看复盘，比学会写脚本更重要。

一、任务是什么

需求：一个编程基础薄弱、主要靠 AI 助手写代码的人，想做羽毛球运动表现分析， 要从零学 YOLO 和骨架分析。需要先把整个技术版图调研清楚。

问题：这个领域涉及 5-6 个互不相干的子领域（目标检测、姿态估计、时序建模、 羽毛球专项研究、工程部署），资料量大，而且新手最容易学到过时的东西 （网上大量教程还在讲 YOLOv5、YOLOv8，而官方已经走到很后面了）。

决策：用模式 1（扇出调研）+ 模式 3（生产者-验证者）。

二、我实际做了什么

一次调用

我给了 workflow 工具两样东西：

meta（身份 + 阶段声明）：

{
  "name": "badminton-ai-research",
  "description": "六路并行调研 YOLO、姿态估计、骨架时序分析与羽毛球专项，再由一个审校 agent 交叉核验",
  "phases": [
    { "title": "调研：六路并行", "detail": "6 个 agent 各自负责一个专题，联网检索后分别落盘" },
    { "title": "交叉审校", "detail": "1 个 agent 读完全部笔记，核对事实并找矛盾与缺口" }
  ]
}

script（脚本正文），骨架就是 examples/04-research-pipeline.js 那个形状：

phase('调研：六路并行')
const notes = await parallel(
  topics.map((t) => () => agent(promptFor(t), { label: t.id + ' · ' + t.title, phase: '调研：六路并行' })),
)
phase('交叉审校')
const review = await agent(reviewPrompt, { label: '审校 · 6 份笔记交叉核验', phase: '交叉审校' })
return { 完成数: notes.filter(Boolean).length, 总任务数: topics.length, 审校: review }

就这些。 脚本本身没有任何"智能"——它只是把 6 个提示词发出去、等结果、再发第 7 个。

提示词里的三个关键设计

设计 1：每个 agent 必须自己落盘，只回传短摘要

请把最终笔记写入这个文件（用 write 工具创建）：
D:/program/learn-ai-coach/research/01-YOLO技术全景与硬件选型.md

写完后，只返回不超过 8 行的中文摘要。

结果：6 份笔记共 约 74 KB（8528 + 12619 + 16252 + 14056 + 11431 + 16544 字节）落到了磁盘上， 而回到主 agent 上下文里的，只有 6 段八行摘要。

这是多 agent 最实用的一招。 如果让 6 个 agent 把全文回传，主 agent 的上下文当场就满了， 后面的审校、汇总、写教程全都没法做。

设计 2：给每个 agent 划互斥边界

你的专题：YOLO 技术全景与硬件选型
必须覆盖：……

6 个专题刻意不重叠。这条不做，6 个 agent 会各写一遍 YOLO 简介。

设计 3：强制统一格式

同一段 COMMON 要求被拼进 6 个提示词：

全中文，Markdown。结构：一句话结论 / 核心概念 / 可执行的最短路径（带真实命令）
/ 选型建议 / 常见坑 / 参考链接。
每篇最后加一节「给 AI 编程助手的提示词」。

最后那一节是副产品设计：既然阅读者主要靠 AI 助手写代码，就让每篇笔记顺便产出 "以后该怎么向助手提这个需求"。你会在 6 份笔记末尾都看到它。

三、结果：数字

指标 实际值
参与的 agent 数 7（6 个调研 + 1 个审校）
阶段数 2
产出文件 7（6 份笔记 + 1 份审校报告）
产出总量 约 101 KB / 721 行
回到主 agent 上下文的 约 30 行摘要
审校发现的问题 43 条编号问题 + 8 处跨文件矛盾 + 8 个结构性缺口
审校自己标注"待复核"的 5 处

这就是扇出 + 验证者模式的实际收益： 用一次工具调用换到 100 KB 的结构化资料，并且知道这 100 KB 里哪些地方不可信。

四、审校环节到底抓到了什么（最重要的一节）

审校 agent 的报告有 93 行、分 5 节。挑三个最有代表性的：

案例 A：版本选型，6 个 agent 各说各话

笔记 它推荐什么
01 "从 yolo11n-pose.pt 起步""YOLO26 更强但资料少"
03 两个并列，没给结论
05 直接推 yolo26n-pose / yolo26s-pose
02 主线写的是 yolo26n.pt

问题是：01 给出的"资料少所以别用 YOLO26"这条理由，在官方文档已经更新之后不成立了。 审校 agent 联网核对后给出仲裁：

新项目直接用 yolo26n-pose.pt（同为 2.9M 参数，COCO 关键点 mAP50-95 57.2， 而 yolo11n-pose 是 50.0）；yolo11n-pose.pt 保留仅作为回退。

这个结论是任何一个单独的调研 agent 都给不出来的——它们各自看到的只是自己那块拼图。

📌 教训 1：扇出一定会制造口径不一致。 如果你只做扇出、不做收口，你拿到的不是"6 份资料"，而是"6 个互相打架的答案"， 而你作为新手没有能力判断谁对。收口（仲裁）环节不是可选项，是必需品。

案例 B：整套资料里最严重的一致性缺陷

01 和 06 把"从关键点算关节角度"当成核心卖点：

"出关键点 → 算关节角度""肘/肩/腕/髋/膝正好覆盖挥拍角度"

而 04 和 05 明确警告：

"不要用 2D 像素坐标算角度""论文里那些关节角度全部来自 3D 动捕，单目手机视频算不出真值"

这两组说法是直接冲突的，而且新手看不出来——因为两组话分开读都很有道理。

审校 agent 的判定是 04/05 对，并要求给所有角度指标加上"2D 投影角"的限定和误差量级说明 （它引用的对照研究里，单目相对 3D 动捕会系统性低估髋角约 11.2°、膝角约 10.6°）。

📌 教训 2：AI 在"A 和 B 冲突"这件事上，比在"A 对不对"上更可靠。 让单个 agent 自查"我写得对吗"，它倾向于说对； 让一个 agent 拿两份稿子对照"这两个说法冲突吗"，它能立刻指出来。 矛盾检测是多 agent 性价比最高的用法。

案例 C：6 个 agent 集体漏掉的那条主线

审校报告里最尖锐的一条：

02 之外无人提球；02 提了但用错方法。 后果：击球帧、击球点高度、落点、球速、回合节奏这五个最贴近"运动表现"的量， 全套笔记里没有可靠来源。

而 05 自己在引用论文时其实已经说出了答案——"球轨迹是主线索而非辅助"—— 却只在角落里提了一句。

注意这件事的性质：这不是某个 agent 写错了，而是6 个 agent 各自的视野里都合理， 合起来却缺了一整条主线。目标检测的 agent 讲检测，姿态的 agent 讲骨架， 谁也不觉得"球"是自己的责任。

📌 教训 3：单点错误靠验证者，系统性盲区靠"全局审阅者"。 所以审校那个 agent 的提示词里，我特意加了第 3 条要求： "找出明显缺口：对'羽毛球运动表现分析'这个目标，还有什么关键环节没人讲。" 如果只让它"找错"，这个盲区永远不会被发现。

五、审校 agent 也诚实地说了"我不知道"

报告的最后两节值得单独看：

  • 未复核：各类精度数字的原始实验条件、生物力学误差数字的原文细节、 TrackNetV3 仓库的权重文件名与 train.py 参数（受网络限制）。
  • 未打开全文、仅依据搜索结果判定的项：……这些在文中已标注"待复核"，请在使用前自行打开确认。

它列了 5 处自己也没核实成功的地方，明确标成"待复核"。

📌 教训 4：一个会承认"我不确定"的验证者，才是可信的验证者。 反过来：如果审校 agent 返回的是"全部检查完毕，没有发现问题"—— 那多半不是好消息，而是它没认真查。 验收验证者的产出时，看它有没有"待复核"清单。没有 = 大概率在敷衍。

六、这次运行暴露出的能力边界

诚实记录，避免你把多 agent 想得太神：

局限 这次的具体表现
不能替代领域专家 6 个 agent 都把"单目能不能算关节角"当成一个技术细节，没意识到这是整个项目能不能立住的前提
审校也查不出源头错误 审校能发现"两份笔记冲突"，但没法判断两份都错的情况
核实受网络限制 有 5 处因为打不开原文而只能标"待复核"
不知道你的真实约束 所有 agent 都不知道你"Python 实操很少、主要靠 AI 助手"——这个信息是我在本次会话里问出来的，不是它们调研出来的
会给你一个"看起来完整"的假象 74 KB、结构整齐、有链接——它给人的确定感，远高于它实际的确定度

最后一条最危险，展开说：

一份排版精美、带引用链接、覆盖全面的调研笔记， 读起来像是"已经调研清楚了"。 但审校报告告诉我们：里面至少 12 处数字是错的、3 条命令跑不通、一整条主线缺失。

多 agent 让产出的"量"和"表面质量"提升得很快，让"正确性"提升得很慢。 所以——验证环节的投入，不该少于生产环节。

七、这次运行教给你的五条

  1. 扇出必须配收口。 6 路调研 + 1 路仲裁，比 7 路调研有价值得多。
  2. 让 agent 落盘，只让它回传摘要。 否则上下文会被撑爆，后面的活全干不了。
  3. 验证者的提示词要显式授权挑错，并给它核实手段。 不授权，它会敷衍。
  4. 除了"找错"，还要让验证者"找缺口"。 系统性盲区只有全局视角能看见。
  5. 看到整齐的产出，先找它的"待复核"清单。 没有，就是可疑信号。

八、你现在可以自己复现

examples/04-research-pipeline.js 就是这个流程的简化可运行版本（3 个专题走 2 个 stage）。

建议的最短路径：

  1. 打开 examples/01-hello-fanout.js，原样跑一次 —— 感受"同时开 3 个 agent"
  2. 换成你自己的 3 个真实问题
  3. 加上 examples/02-producer-verifier.js 的审校阶段 —— 这一步会让你改变对 AI 产出的信任度
  4. 打开 GUI 看那几张小卡片，观察它们什么时候起、什么时候落

跑完第 3 步，你就真正理解多 agent 的价值在哪了。
