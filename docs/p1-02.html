02 · DSH 的多 agent 机制全解

这一篇讲的是你现在正在用的这套 harness 内部真实的机制，不是通用科普。 里面提到的每一行配置，都能在你的机器上找到对应文件。

一、先建立一张地图：两个平面

DSH 里的一切能力都是一行配置（Cordis 的 plugin row）。这些行分成两个平面：

┌──────────────────────────── 进程级（一个进程一份） ────────────────────────────┐
│  HOST 组成 (host composition)                                                 │
│                                                                               │
│   · 各种注册表：tools / systemPrompt / agents / agent-loop / sessions          │
│   · 会话持久化、设置、凭据、遥测                                                │
│   · 沙箱 & 审批栈、模型路由                                                     │
│   · ★ subagents 注册表 + 它的 spawn / fork 后端  ← 多 agent 的地基在这里        │
└───────────────────────────────────────────────────────────────────────────────┘
                                     ▲ 装载
┌──────────────────────────── 会话级（每个会话一份） ───────────────────────────┐
│  AGENT PRESET（agent 预设）                                                    │
│                                                                               │
│   · persona（人格设定）                                                        │
│   · 这个 agent 能用哪些工具                                                     │
│   · 压缩策略（上下文满了怎么办）                                                │
│   · ★ 委派工具（subagent / subagent_fork / workflow / ralph）← 只是"工具"      │
└───────────────────────────────────────────────────────────────────────────────┘

关键推论：多 agent 的"发动机"在 host 里，preset 只决定"这个 agent 有没有方向盘"。

为什么这么设计？因为 subagents 注册表是进程单例——浏览器的 agent 列表要跨会话查询它。如果它放进 preset，第二个会话挂载时就会撞名报错。

这一条是新手写 preset 时最常犯的错，记住它：会"提供服务"的行，不能随便放进 preset。

二、你的工具箱：四种"分身"

DSH 给你四把不同的刀。它们的区别不是"哪个强"，而是"哪种上下文关系"。

1. subagent —— 全新的员工

项目 说明
上下文 全新的，看不到你和它的对话历史。你给它的 prompt 必须自包含
模型 可以指定别的模型（modelSelectionSettings: true 时）；适合"用便宜模型干粗活"
后台 默认后台，立刻返回一个 id，跑完通知你
持续对话 可以。跑完后你可以再用 send_message 给它派新活
拿回什么 只有它的最终文本。中间步骤你看不见

什么时候用：一块自包含的活（"去把这个目录的文件都读一遍，总结成表"）。

最常犯的错：prompt 写得太短，默认它知道你在聊什么。它什么都不知道。

❌ "帮我把上面那个改了"          → 它不知道"上面"是什么
✅ "在 D:\program\x\a.py 里，把第 30 行的 timeout 从 60 改成 120。
    改完把改动前后的行贴给我。"

2. subagent_fork —— 带着记忆分家

项目 说明
上下文 继承你到目前为止的全部对话（不含当前正在进行的这一轮）
模型 强制和父 agent 相同。原因：继承的历史能命中 KV cache，换模型就白费了
适合 "接着我们刚才聊的这件事，你去深挖一下"

什么时候用：任务建立在你俩已有的上下文上（复盘、审查、续写）。

省钱的原理：fork 出来的子 agent 复用了父 agent 已经算过的 KV cache，比 subagent 重新喂一大段背景更便宜。所以能用 fork 就别用 spawn 加长 prompt。

3. workflow —— 你写调度脚本，它开一堆 agent

这是唯一让你"编程"控制多个 agent 的入口。你写的是一段 JavaScript，脚本本身不调用大模型，它只负责调度：

phase('调研：六路并行')
const notes = await parallel(
  topics.map((t) => () => agent(promptFor(t), { label: t.title, phase: '调研：六路并行' }))
)
phase('交叉审校')
const review = await agent(reviewPrompt, { label: '审校' })
return { 完成数: notes.filter(Boolean).length, 审校: review }

这是本教程的主角，单独一篇讲：04-workflow脚本编写.md。

4. ralph —— 不断换新人的循环

同一个不可变的目标，一轮一轮开全新的 agent 去冲。每轮都是干净上下文，工作区里的文件就是它唯一的记忆。

什么时候用：目标是明确的、可验证的（"让这个测试通过"），但路径不确定，需要反复试。必须把进展写在文件里。

什么时候别用：目标模糊、或者需要连续对话才能推进的活。

三、配套的"管理"工具

开分身容易，管分身难。这三个工具是配套的：

工具 作用 典型用法
list_agents 列出你的子 agent（id / 标签 / 状态） 忘了自己开了几个、谁还在跑
send_message 给某个子 agent 发消息 它在跑 → 转向它的下一步；它空闲 → 给它开新一轮
interrupt_agent 打断某个 agent 当前的这一轮 发现方向错了，别等它跑完

注意 send_message 的语义：它不是提问，是投递。调用成功只代表"消息送到了"，不代表对方会立刻回你。你需要等它完成时系统给你的通知。

四、怎么选：一张决策表

你的情况 用哪个
一块独立的小活，和当前对话无关 subagent（后台）
接着当前对话继续挖 subagent_fork
同一套流程要跑很多份素材 workflow + pipeline
一大批互不依赖的活要同时开 workflow + parallel
需要结构化结果（表格、字段）而不是一段话 workflow + agent(..., { schema })
要反复试错直到达标 ralph
就改个错别字 别用，自己改

五、钱和上下文：两个必须理解的机制

机制 1：为什么子 agent 能省上下文

子 agent 的过程（读了 20 个文件、试了 5 种方案）全部发生在它自己的上下文里。回到你这儿的只有一段最终文本。

不隔离：你读了 20 个文件 × 5000 字 = 10 万字塞进你的对话
隔离后：6 个 agent 各读 20 个文件，你只收到 6 × 300 字 = 1800 字

代价：细节丢了。如果它得出了错误结论，你看不见它是怎么错的。所以—— 重要产物要让 agent 自己写进文件，而不是只让它"说给你听"。文件是它留给你的完整过程，返回文本只是索引。

机制 2：为什么 fork 比 spawn 便宜

KV cache。父 agent 已经算过的对话前缀，fork 出来的子 agent 可以直接复用。换模型 / 改前缀都会让 cache 失效，所以 DSH 强制 fork 的子 agent 用同一个模型。

实践结论： - 任务能用已有上下文描述 → subagent_fork - 任务完全独立 → subagent，但 prompt 要写全 - 不要为了"省钱"把一大堆背景塞给 subagent——那正是 fork 该干的活

六、在 GUI 里看见它们

多 agent 不是黑盒。你在这个 Web GUI 里能直接看到：

  • 每个子 agent 是一个独立的会话，有 id 和标签（就是你传的 label）
  • 状态：running（正在干活）/ idle（在等你派活）/ ready（只在存储里，可以唤醒）
  • 派活的消息投递失败会明确报错——不会静默丢掉

给你的第一个实操建议：打开一个 workflow 或开几个 subagent，然后盯着 GUI 看。看它们什么时候起、什么时候落、返回了什么。一两次之后你就对"多 agent 到底在发生什么"有实感了。
