# 01 · 为什么需要多 agent，什么时候不需要

> 这一篇不讲工具，只讲判断。工具随时可以学，判断错了再好的工具也是浪费钱。

## 一、先破除一个误解

多 agent **不是**"让 AI 变得更聪明"。

同一个模型，你把它拆成 5 个 agent，它们的智商没有任何变化。多 agent 买到的是三样东西：

| 买到的东西 | 是什么意思 | 什么时候值钱 |
|---|---|---|
| **上下文隔离** | 子 agent 读的 5 万字资料，不会塞进主 agent 的对话里 | 资料量大、且大部分是噪音时 |
| **并行** | 6 件事同时做，而不是排队做 | 任务之间互不依赖时 |
| **独立视角** | 一个 agent 挑另一个 agent 的错，它没有"我刚写的，我不能打自己脸"的包袱 | 需要正确性，而不是"看起来对"时 |

反过来，多 agent 要付的成本：

- **协调成本**：你要写清楚每个 agent 干什么，比你自己干还费脑子
- **Token 成本**：6 个 agent 就是 6 份起步开销，扇出调研一次轻松烧掉几十万 token
- **信息损耗**：子 agent 只能靠一段文字把结论交回来，中间过程的细节全丢了
- **假象风险**：6 个 agent 都答错同一个问题时，你会因为"多数一致"而更相信那个错误（比单 agent 更危险）

**结论：多 agent 是"并行 + 隔离 + 交叉验证"的工程手段，不是能力升级。**

---

## 二、单 agent 的三个天花板

你会自然而然地想用多 agent，通常是因为撞到了下面某一面墙：

**1. 上下文墙**
你让它读 30 篇论文然后写综述。读到第 20 篇时，前面 10 篇已经被压缩/遗忘了，写出来的东西开始"凭印象"。

**2. 注意力墙**
一个 agent 同时扮演"产品经理 + 架构师 + 程序员 + 测试 + 技术写作"，它会在不同角色间反复横跳，通盘质量下降。这不是玄学——角色和目标写在同一个 prompt 里，指令会互相干扰。

**3. 串行墙**
"帮我调研 6 个方向"，一个 agent 串行做完要 6 倍时间。而这 6 件事之间没有任何依赖。

## 三、五种协作模式（本教程的主要骨架）

这五种模式覆盖了 95% 的实际需求。**记住这五张图，比记住工具名有用得多。**

### 模式 1：扇出调研（Fan-out / Map）

```
         ┌──→ 调研员 A ──→ 笔记 A ──┐
         ├──→ 调研员 B ──→ 笔记 B ──┤
主 agent ─┼──→ 调研员 C ──→ 笔记 C ──┼─→ 汇总
         ├──→ 调研员 D ──→ 笔记 D ──┤
         └──→ 调研员 E ──→ 笔记 E ──┘
```

- **特征**：子任务同质、互不依赖、可以乱序完成
- **买到**：并行速度 + 上下文隔离
- **风险**：五个人可能重复劳动、口径不一致
- **必须做**：给每个人一个**互斥的边界**（"你只负责 X，不要碰 Y"），并且要求**统一格式**
- **DSH 工具**：`workflow` 的 `parallel([...])`，或者直接开几个 `subagent`

### 模式 2：流水线（Pipeline）

```
素材1 ──→ 提取要点 ──→ 交叉验证 ──→ 成稿
素材2 ──→ 提取要点 ──→ 交叉验证 ──→ 成稿
素材3 ──→ 提取要点 ──→ 交叉验证 ──→ 成稿
        （每一条独立跑完全程，不等别人）
```

- **特征**：每个素材都要走**同一串**处理步骤，但素材之间互不相干
- **和模式 1 的区别**：模式 1 是"一个阶段"，模式 2 是"多个阶段"
- **关键优势**：中间**没有栅栏**——素材 1 已经到第三步时，素材 3 可能还在第一步。整体吞吐远高于"所有素材都跑完第一步才开始第二步"
- **DSH 工具**：`workflow` 的 `pipeline(items, stage1, stage2, ...)`

### 模式 3：生产者—验证者（Adversarial）

```
写手 ──→ 初稿 ──→ 审校（专门挑错）──→ 问题清单 ──→ 修订
```

- **特征**：一个 agent 产出，**另一个 agent 的唯一目标就是推翻它**
- **为什么有效**：AI 有一个很顽固的毛病——**它会给自己刚写的东西背书**。让它"再检查一遍"，它倾向于说"检查过了，没问题"。换一个没有这段上下文的 agent，它才能真的挑出毛病
- **必须做**：审校 agent 要拿到**明确的挑错许可**（"你现在的任务是找出错误，找到越多越好"），还要给它**核实手段**（联网搜索、读原始文件）
- **DSH 工具**：开一个 `subagent` 专门做验证；或 `workflow` 里 phase 2

> 本教程的这一套文档就是这么产出的。见 `05-实战复盘.md`——6 份调研笔记的审校环节挑出了 **43 条具体问题**，包括 3 处直接跑不通的命令和 1 个跨文件自相矛盾的严重错误。

### 模式 4：主管—工人（Orchestrator）

```
              ┌─→ 工人1 ─→ 汇报
主 agent ─────┼─→ 工人2 ─→ 汇报 ─→ 主 agent 决定下一步
（看汇报做决策）└─→ 工人3 ─→ 汇报
```

- **特征**：主 agent 不做事，只**看汇报、下指令**，多轮推进
- **和模式 1 的区别**：模式 1 是"一次扇出，一次收口"；模式 4 是**多轮循环**，下一批任务取决于上一批的结果
- **DSH 工具**：`subagent`（可后台、可持续对话）+ `send_message` 追加指令 + `list_agents` 查看状态

### 模式 5：新鲜循环（Ralph）

```
目标 ──→ 工人（全新上下文）──→ 状态落盘 ──→ 下一轮工人（全新上下文）──→ ...
                                      ↑
                             工作区就是记忆
```

- **特征**：同一个目标，反复换**全新的** agent 来冲，每一轮都不携带上一轮的对话
- **为什么有用**：长会话会累积"错误共识"和上下文垃圾。换个新人，它会用干净的眼光重新读代码/文档，常常一眼看出老 agent 绕了半天的坑
- **关键要求**：**记忆必须落在文件里**（否则新 agent 一无所知），并且要有**可验证的完成标准**
- **DSH 工具**：`ralph`

## 四、什么时候**不要**用多 agent

这一节比上一节更重要。

**❌ 不要拆的**：

1. **紧密耦合的编码任务**
   "你写前端，你写后端，你写数据库"——三个人对接口的想象是不一样的，最后合不起来。**代码库里同时改多个文件的活，交给一个 agent。**

2. **需要连续判断的调试**
   排查一个 bug 需要"改一点 → 看结果 → 再改"。这是串行的、强依赖的，拆开只会让每个人重新理解一遍问题。

3. **你自己没想清楚的任务**
   多 agent 会把你思路里的模糊放大 N 倍。**先自己想清楚"要什么产物"，再拆。**

4. **小任务**
   改个错别字、写个 20 行的脚本。多 agent 的协调开销大于收益。

**✅ 值得拆的**：

- 调研 / 资料收集 / 横向对比（无依赖、量大）
- 同一份产出要**多角度审查**（安全、性能、可读性各一个）
- 重复性批量操作（100 个文件逐个改，每个文件独立）
- 需要**独立视角**的判断题（"这个方案到底行不行"）

---

## 五、一条经验法则

> **能不能拆，看两件事：子任务之间有没有依赖？每个子任务能不能独立验收？**

两个都是"是" → 放心拆。
有一个是"否" → 要么别拆，要么你先花力气把边界和验收标准定义出来。

**没有验收标准的多 agent，等于雇了 6 个人然后不检查他们的工作。**
